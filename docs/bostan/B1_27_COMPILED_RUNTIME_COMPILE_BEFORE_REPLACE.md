# B1-27 — Compile before replacing a previously qualified runtime

Date: 2026-10-29. **Private** Bostan, stacked Draft only. Exact parent: B1-26 PR #279 at `f94a1dcf27e988a1ba8737352a478d83d98c3a1d`.

## Actual source defect

The original `server/scripts/bundle-runtime.mjs` called `rm(admittedOutdir, {recursive:true,force:true})` **before** `await build({...})`. Even a normal source compilation or import-resolution error erased the previously built and ownership-verified `index.mjs`/`server.mjs`, taking away a potentially functional offline runtime. This is an availability/recoverability failure distinct from the prior B1-23–B1-26 path and source-link protections. No destructive baseline execution was used.

## Change

`bundleRuntime` now calls `buildAndCommitCompiledRuntime`, which verifies the existing destination, forces esbuild to `write:false`, and only considers replacing the existing runtime after esbuild has successfully returned all generated `outputFiles`. `commitCompiledRuntimeOutputs` rejects any output path outside the exact admitted directory, unexpected extension/nested directory, duplicate name, malformed contents or missing `index.mjs`/`server.mjs`. It caps total in-memory generated bytes at 512 MiB and at most 10,000 files. A second safety admission runs immediately before deletion. Only then are the verified generated outputs written with exclusive creation and the existing Bostan ownership manifest recorded.

Compilation failures and validation/admission failures therefore retain the previous version unchanged. The full generated output must be held in memory, which increases peak RAM versus directly writing to disk and can fail under constrained memory. It intentionally fails closed rather than bypass the cap or risk unowned file deletion.

## Executed evidence

An isolated local Linux Node.js 22.16 run of `bundle-runtime-commit.mjs` with injected synthetic build callbacks and synthetic TEMP fixtures passed syntax checks and **6/6 tests**, zero failures. Those tests cover successful prepared replacement, simulated compilation rejection with original contents preserved, invalid/escaping/duplicate output rejection without deletion, last-moment admission refusal, forced `write:false` despite caller options, and a valid callback's success output.

**Not performed:** real Windows esbuild 0.28.2 compiled runtime regression, native Windows full compiled server and 18-stage localhost HTTP/BetterAuth, actual PostgreSQL orphan multi-suite, Chromium, macOS E2E, free local agent and installer. Both connected computers were offline at this wave's start. The local tests exercise the tested helper's behavior; the full pinned esbuild integration remains a separate gate.

**Important limitation:** this does NOT make replacement atomic. A disk error, crash or hostile concurrent filesystem change **after** the final admission can leave a partial, unowned output; fail-closed admission then prevents automatic deletion or recovery. Do not report the transaction as fully atomic or issue #237 fixed. To achieve robust restart safety, a future separate rollout needs an independently qualified same-volume staging+promotion/rollback strategy without deleting unowned data.
