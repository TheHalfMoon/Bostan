# B1-234 — Pin an explicit physical PostgreSQL toolchain for local qualification

Date: 2026-11-07 Asia/Riyadh. **PRIVATE / OPEN DRAFT / UNMERGED / RELEASE NO-GO.**

## Actual source-backed executable-origin issue

The local synthetic PostgreSQL migration qualification script called `spawnSync('initdb', ...)`, `spawnSync('pg_ctl', ...)`, etc. by **bare executable name** at both version preflight and actual cluster initialization/start, migration backup and stop. Its `PATH` came from the operator's environment. Therefore the preflight command could be satisfied by one executable and a later command could resolve a different program after a `PATH` or file replacement; untrusted programs on `PATH` could also run before any protective PostgreSQL process proof.

A locally owned Linux Node22 real-filesystem test generated six synthetic executable test scripts in a verified, private binary folder and placed an unrelated synthetic `psql` earlier on `PATH`. Invoking the **explicit pinned absolute path** executed the intended test program rather than the shadow. This is not a real PostgreSQL run or a proof of system package authenticity.

## Implementation

New `scripts/bostan-local-postgres-toolchain.mjs` requires an owner/operator-selected, absolute, physical `BOSTAN_PG_BIN_DIR`, evaluated by the parent runner before creating any scratch. It checks that the directory is real (no symlink alias), ordinary and non-group/world-writable on POSIX, and that **all six tools** (`initdb`, `pg_ctl`, `createdb`, `psql`, `pg_dump`, `pg_restore`) are ordinary, nonlinked, singly-linked files in that directory, executable and not group/world-writable on POSIX. Windows uses local-drive-rooted paths only (no UNC/device namespace) with native `.exe` names. It captures the `dev`, `ino`, and `birthtimeMs` of bin directory and each executable, and revalidates their identity before every corresponding subprocess use. Failed or changed paths refuse before running a subprocess, with fixed path-free error text.

The actual `scripts/bostan-local-postgres-migration-qualification.mjs` now captures this registry **after pure Cloud admission and before `mkdtempSync`**, and routes every PG binary version probe, `initdb`, `pg_ctl start/stop`, `createdb`, `psql`, `pg_dump`, and `pg_restore` through its absolute verified physical path in `qaExec`. The pinned registry is separate from the scrubbed child environment. `qaExec` still verifies the B1-232 private child profile before spawning any program. Safe diagnostic labels remain the allowlisted original tool name, never the sensitive absolute pinned path; `pnpm` remains separately subject to existing profile and offline restrictions. The `--help` output explicitly requires `BOSTAN_PG_BIN_DIR` for `--run`.

## Limits / outstanding release gates

This is not cryptographic authenticity of the installed PostgreSQL distribution, a kernel-backed file-handle execution mechanism, sandboxing, or an atomic check-to-exec guarantee against a concurrent privileged attacker. A user/operator who selects a malicious `BOSTAN_PG_BIN_DIR` can still authorize a malicious toolchain initially; such input must be trusted and ideally version/hash verified. Strict non-symlink physical paths can require operators of Homebrew or other linked installations to select the actual versioned `bin` directory. Real Windows path handling and POSIX toolchain completeness require native qualification. The explicit directory is a new deliberate requirement, not automatically downloaded or resolved via operator `PATH`.
